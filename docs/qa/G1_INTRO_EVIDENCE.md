## CSS viewport와 캡처 위젯은 다르다

모든 screencast metadata의 `deviceWidth/deviceHeight`는 **1280×720**이고 `offsetTop`, `scrollOffsetX/Y`는 0이다. JPG는 이 위젯 전체를 작은 크기로 축소한 결과다. emulated app 바깥의 빈 영역도 들어 있다. 예를 들어 667×375 JPG가 CSS viewport와 같은 숫자라고 해서 앱만 1:1로 캡처됐다는 뜻은 아니다. 실제 확인한 JPG에서 앱은 좌상단 일부이고 나머지는 위젯의 빈 영역이다.

390×844의 CSS viewport 아래 **124px**는 720px 위젯 밖이다. 따라서 이 자료를 **390×844 전체 viewport 영상**이라고 부를 수 없다. 다만 해당 trace의 책 전체 envelope는 `x=15.236…364.589, y=207.474…652.756`이며, 기록상 책은 위젯 하단보다 **67.244 CSS px 위**에 있다. 360×640의 책 최대 bottom도 531.842이다. 나머지 조건을 포함해 기록된 책 bounds는 모두 `0…1280 × 0…720` 안에 있다. 좌상단 앱 배치는 실제 JPG와도 맞는다.

결론적으로 **현재 자료에서 책 본체가 위젯에 잘렸다는 증거는 없으며 수치상 잘리지 않는다.** 그러나 portrait 전체 viewport, 앱 바깥으로 잘린 모든 내용, 실제 주소창·휴대전화 화면까지 검증했다고 확대하지 않는다. 1280×720 위젯의 축소 캡처라는 한계를 함께 남긴다.

## 시각 표본과 진행률의 한계

편집하지 않은 실제 JPG를 열어 확인했다: 844×390의 index12/28/41, 667×375의25, 568×320의44, 390×844의20/41, 360×640의43, 비대칭 조건의43. 제공된 닫힌 표지와 본체가 보이고 선택 표본에서 책 본체 clipping은 보이지 않는다. 844×390의 세 표본에서는 크기·위치의 진행 변화가 보인다. 이 번호는 **원본 frame index**이며 25/50/75%라는 뜻이 아니다.

trace는 `records[].time`의 performance 기준 ms를 저장하지만 `performance.timeOrigin`, epoch/monotonic 기준점 또는 공통 frame ID를 저장하지 않았다. JPG manifest에는 epoch `timestamp`와 `metadata.monotonicTimestamp`가 있으나 trace 시계와 연결할 값이 없다. 종료 표본끼리 맞추거나 비례 보간하여 offset을 추측하지 않았다. 따라서 **특정 JPG와 정확한 introProgress의 대응은 unknown**이다. 첫/마지막 raw frame도 자동으로 0/100%로 표시하지 않는다.

가장 가까운 **trace 수치 표본**은 별도로 보존했다(아래는 actual progress; raw frame과 연결되지 않음).

## 판정 범위

- **수치 확인:** 여섯 조건의 기록된 intro 전체 진행 범위에서 bounds 안전, 최종 중앙 정합, camera 변화 및 자동 audio source 없음. 이 확인을 캡처 형식의 한계 때문에 실패로 되돌리지 않는다.
- **시각 확인:** 위에 명시한 원본 JPG에서 실제 표지·본체·진행 변화 및 축소된 위젯 밖 빈 영역을 확인했다. 전체 CSS viewport를 정확히 담은 영상이나 동기화된 0/25/50/75/100% 이미지 세트는 아니다.
- **남은 증거:** 정확한 중간 진행률 시각 대조가 필요하면 performance.timeOrigin 또는 공통 frame/event ID를 함께 기록한 새 캡처를 사용한다. 전체 portrait 영상이 필요하면 캡처 surface가 CSS viewport 전체를 포함하는지 먼저 확인한다. 이는 현재의 수치 통과와 구분되는 증거 보완이다. CI03·열린 책·터치·청취 등은 이번 검토 범위가 아니다.
